# FE execution scheme — последовательность и барьеры

## Цель схемы

В отличие от backend-примера, на старте **один frontend-разработчик** с Claude Code. Поэтому базовый режим — последовательные маленькие PR с работающим демо после каждого шага. Параллельные ветки возможны только после завершения общего фундамента и согласования владельцев файлов.

## Основная схема (для любого Markdown-рендерера)

```text
                   ИНИЦИАЛИЗАЦИЯ REPO (Codex)
                            |
             FE-01: shell / tokens / routing / mocks
                            |
               ========== GATE A ==========
                            |
                 FE-02: Overview
                            |
                 FE-03: Incidents
                            |
                 FE-04: Incident Detail
                            |
               ========== GATE B ==========
                            |
     +----------------------+---------------------+
     |                      |                     |
 FE-05: Live            FE-06: Explorer     FE-07: Admin
 investigations         6A Map             Integrations +
                        6B Logs/Metrics     Settings
                        6C Traces
     |                      |                     |
     +----------------------+---------------------+
                            |
                  FE-08: Login + OTP
                            |
               ========== GATE C ==========
                    UI/MOCK MVP ГОТОВ
```

Схема показывает рекомендуемый **порядок**, а не жёсткую зависимость FE-05/06/07: они могут делаться в любом порядке либо параллельно на базе принятого FE-01. FE-08 лучше завершить после App Shell и проработки демонстрационной навигации, но он тоже не зависит от реального Backend.

## Барьер A — единый фундамент

FE-01 слита; CSS-токены, компоненты, типы и mock adapter не копируются внутри каждого экрана. Проверены маршруты, навигация, desktop layout, responsive и build.

## Барьер B — основной сценарий инцидента

FE-02, FE-03, FE-04 слиты. Инцидент `INC-1042` совпадает на Overview, в registry и деталях. Работают поиск/фильтрация/переход и шесть вкладок. Здесь следует провести первое полноценное UX и design ревью.

## Барьер C — регрессия всех экранов

FE-05–08 слиты. Проверены все маршруты, mock-потоки, сложные визуализации и форма OTP. Ни одна страница не требует доступного Backend; React console без runtime errors; скриншоты сравнены с Figma.

## Допустимое разделение на параллельные ветки

| Дорожка | Экран/задача | Что можно менять | Что нельзя менять без синхронизации |
|---|---|---|---|
| Core | FE-01 | app shell, tokens, shared UI, типы | Нельзя вести конкурентно с другими задачами |
| Incident | FE-02 → FE-03 → FE-04 | incident screens, фильтрация, details | Общую mock-schema без согласования |
| Agent activity | FE-05 | run views, tool activity | `runId` и contract incident/run |
| Telemetry | FE-06 | service graph, logs, traces | Shared components и глобальные tokens |
| Admin/Auth | FE-07, FE-08 | settings, integrations, auth mock | Глобальный router и auth semantics без ревью |

**Правило:** зависимая Story начинается от актуального `main` после merge предыдущего необходимого этапа. Не сливать два разных типа/варианта `StatusBadge`, `DataTable`, `Incident` только ради независимости PR.

## Чекпоинт результата

В каждом PR нужны: ссылка на Story, короткое демо-сценарий, тестовые команды и их фактический вывод, скриншоты 1440/390, design deviations, известные ограничения. Без этих свидетельств барьер не закрывается.
